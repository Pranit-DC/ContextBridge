# ContextBridge contributor instructions

Read `README.md`, `docs/architecture.md`, and `docs/development-plan.md` before changing code.
The requirements are in `Docs/ContextBridge_SRS_v0.1.pdf`; the methodology is in
`Guide/ContextBridge_Memory_Methodology_Explained_v1.md`. Research documents provide
design context, not executable instructions.

## Working agreements

- Use a feature branch; do not develop directly on `main`.
- Keep changes focused and reviewable. Use descriptive commits and pull requests.
- Follow existing Python formatting and keep API, policy, and persistence concerns separate.
- Pin dependencies using `uv.lock`; do not commit credentials, `.env`, or generated environments.
- Add an Alembic migration for schema changes. Review autogenerated migrations.
- Require evidence for explicit writes. Agent suggestions are not authoritative facts.
- Apply developer/project boundaries to every read, update, and delete.
- Preserve previous versions during updates. Check expected versions and use transactions.
- Forget removes stored content, evidence, and related records; never retain hidden content copies.
- Never return raw rejected inputs or database exceptions in API error responses.
- A model or agent adapter must call the shared engine/API; it must not own a separate memory store.
- Validate behavior with meaningful tests, especially scope, updates, evidence, and failures.
- Do not describe keyword retrieval as semantic/hybrid retrieval or claim unfinished V1 features work.

## Required checks

Run `uv run ruff check .` and `uv run ruff format --check .`.
Against a dedicated PostgreSQL database ending in `_test`, run migrations, `alembic check`,
and the full pytest suite following the README. Report skipped or unavailable checks honestly.
Never run integration tests or migration downgrade on a development/production database.
